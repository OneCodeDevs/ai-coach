## Was ist ein Prompt?

Ein **Prompt** ist der Text, den du an ein Sprachmodell schickst — also deine Eingabe, auf die das Modell reagiert. Das kann eine einfache Frage sein („Was ist die Hauptstadt von Frankreich?"), aber in der professionellen Arbeit mit LLMs ist ein Prompt deutlich mehr: Er ist eine **Schnittstelle** zwischen dir und dem Modell.

Der entscheidende Punkt: Was du nicht spezifizierst, füllt das Modell mit dem Wahrscheinlichsten. Bei einer Quizfrage ist das harmlos. Bei einer Coding-Aufgabe ist „das Wahrscheinlichste" oft der Bug.

## Warum ist Prompt-Struktur wichtig?

Stell dir vor, du gibst einem neuen Kollegen eine Aufgabe — aber ohne zu sagen, welche Codebase er verwenden soll, welche Konventionen gelten, was das gewünschte Ergebnis-Format ist, und wann er fertig ist. Er wird *irgendwas* liefern, und es wird wahrscheinlich nicht das sein, was du wolltest.

Genau so verhält sich ein LLM bei einem vagen Prompt. Es ist nicht faul oder dumm — es hat schlicht nicht genug Information, um die richtige Entscheidung zu treffen.

Die großen Anbieter beschreiben dasselbe Problem mit verschiedenen Metaphern:
- **Anthropic:** „Denk an Claude wie eine brillante neue Kollegin, der die Hausregeln fehlen."
- **OpenAI:** „Klare Instruktionen, Referenzmaterial, aufgeteilte Schritte."
- **Google:** „Prompten ist Strategie, nicht Magie."

## Die vier Teile eines Prompts

Ein gut strukturierter Prompt hat vier Bereiche. Nicht jeder Prompt braucht alle vier — aber wenn einer fehlt, solltest du wissen, dass das Modell diesen Teil *raten* wird.

### 1. Rolle (Wer?)

Die **Rolle** definiert, *aus welcher Perspektive* und *mit welchen Regeln* das Modell antworten soll. Aber Achtung: „Du bist ein Senior-Entwickler" allein ändert fast nichts. Modelle sind bereits auf Hilfsbereitschaft und Code trainiert.

Die Rolle wird nützlich, wenn sie **konkrete Verhaltensregeln** trägt:
- Keine neuen Dependencies ohne Begründung einführen
- Bestehende Patterns im Repo haben Vorrang vor Greenfield-Lösungen
- Bei Unklarheit nachfragen statt erfinden
- Tests müssen grün sein, bevor etwas als „fertig" gilt

Das ist keine Persönlichkeit — das ist Policy. Und Policy gehört oft in den System-Prompt (dazu mehr in einer späteren Lektion), nicht in jeden einzelnen Auftrag.

### 2. Instruktion (Was?)

Die **Instruktion** ist der eigentliche Auftrag. Sie sagt dem Modell, was es *jetzt, konkret* tun soll.

**Schlecht:** „Mach die Auth sauberer."
**Besser:** „Ersetze die Session-Cookies durch die bestehende JWT-Middleware in `src/auth`. Keine neuen Pakete. Danach `npm test` ausführen und nur als fertig markieren, wenn grün."

Der Unterschied: Die zweite Version ist ein Ticket. Die erste ist ein Wunsch.

Tipps für gute Instruktionen:
- Nummerierte Schritte helfen, wenn die Reihenfolge zählt
- Ein Satz reicht, wenn der Auftrag klein ist
- Anthropics Faustregel: Zeig den Prompt einem Kollegen ohne Projektwissen. Wenn der ratlos ist, ist es das Modell auch.

### 3. Kontext (Womit?)

Der **Kontext** ist das Material, auf dem die Antwort stehen soll. Ohne Kontext muss das Modell aus dem Gedächtnis (den Trainingsdaten) antworten — und dort lauern veraltete Informationen und Halluzinationen.

Was guter Kontext sein kann:
- Die Datei mit dem Bug
- Der Stacktrace
- Ein relevanter Ausschnitt der API-Dokumentation
- Zwei Gegenbeispiele (wie es *nicht* aussehen soll)
- Das Ticket oder die User-Story

Was Kontext *nicht* ist: „möglichst viel Repo". Alles, was nicht zur aktuellen Aufgabe beiträgt, ist Lärm — und Lärm kostet Token in jedem Turn (wie du im Kapitel über das Context Window gelernt hast).

In einem Agent-Setup kommt Kontext oft über Werkzeuge: Der Agent liest eine Datei, führt einen Grep aus, startet einen Test. Der Prompt muss dann sagen, *wonach* zu suchen ist — nicht den ganzen Dateibaum einkopieren.

### 4. Format (Wie soll die Antwort aussehen?)

Das **Format** definiert die Gestalt der Ausgabe. Ohne Format-Angabe bekommst du einen frei fließenden Absatz — gemischt aus Code, Erklärungen, Entschuldigungen und Vorschlägen. Das ist in einem Chat manchmal okay, aber in einer Pipeline oder einem Review-Prozess ein Problem.

Beispiele für Format-Angaben:
- „Antworte nur mit dem geänderten Code, keine Erklärung."
- „Gib die Antwort als JSON mit den Feldern `verdict`, `files` und `risk`."
- „Erst ein `<plan>`-Tag mit drei Sätzen, dann der Patch, dann `<test_output>`."
- „Liste nur die Dateipfade, die geändert werden müssen."

Format ist keine Ästhetik. Es ist die Stelle, an der du den Output **prüfbar** machst — ob von einem Menschen oder von einem automatisierten System.

## Zusammenspiel der vier Teile

| Teil | Frage | Wenn fehlt... |
|------|-------|---------------|
| Rolle | Wer bin ich, welche Regeln gelten? | Modell folgt seinem Default-Verhalten |
| Instruktion | Was soll ich jetzt tun? | Modell rät den Auftrag aus dem Kontext |
| Kontext | Auf welcher Basis? | Modell antwortet aus dem Gedächtnis (Halluzinationsgefahr) |
| Format | Wie soll die Antwort aussehen? | Modell liefert unstrukturierte Prosa |

Je mehr Teile du bewusst füllst, desto weniger muss das Modell interpolieren. Und Interpolation — also das Auffüllen von Lücken mit dem Wahrscheinlichsten — ist in Produktionscode ein Defect.

## Ein vollständiges Beispiel

```
[Rolle]
Du bist ein Code-Reviewer. Du prüfst nur auf Korrektheit und
bestehende Konventionen. Keine Style-Vorschläge, keine Refactoring-Ideen.

[Instruktion]
Prüfe den folgenden Diff auf Bugs, fehlende Edge Cases und
Verletzungen der Projekt-Konventionen.

[Kontext]
<diff>
... (der zu prüfende Diff) ...
</diff>

<conventions>
- Error Handling: immer HttpError aus src/errors verwenden
- Keine neuen Dependencies ohne Abstimmung
- Tests für jede öffentliche Funktion
</conventions>

[Format]
Antworte als JSON-Array:
[{"file": "...", "line": ..., "severity": "bug|convention|edge-case", "finding": "..."}]
Wenn alles in Ordnung ist: leeres Array [].
```

Dieses Beispiel trennt klar: Wer prüft (Rolle), was geprüft wird (Instruktion), auf welcher Basis (Kontext), und wie die Antwort aussehen muss (Format).

<Merksatz>
Rolle setzt die Regeln, Instruktion den Auftrag, Kontext das Material, Format den Vertrag. Fehlt ein Teil, interpoliert das Modell — und Interpolation ist in Produktionscode ein Defect.
</Merksatz>
