Diese Lektion bringt drei Themen zusammen, die für den Betrieb eines Produkts unverzichtbar sind: automatische Qualitätsprüfung (CI/CD), sichtbare Fehler (Logging und Fehlerbehandlung) und eine Übergabe, bei der der Gründer *ohne euch* weiterarbeiten kann — inklusive seiner KI-Agenten.

## CI/CD — diesmal als Mindeststandard erklärt

### Was CI/CD nochmal ist (kurze Wiederholung)

**CI (Continuous Integration)** bedeutet: Jedes Mal, wenn jemand Code-Änderungen vorschlägt, werden automatisch Prüfungen durchgeführt — Tests, Codequalität, Sicherheitsscans. Das passiert ohne manuellen Aufwand, bei jedem PR.

**CD (Continuous Delivery/Deployment)** bedeutet: Wenn die Prüfungen bestanden sind und ein Mensch zugestimmt hat, wird die neue Version automatisch veröffentlicht.

**Analogie:** CI ist die TÜV-Prüfung, die jedes Auto bestehen muss, bevor es auf die Straße darf. CD ist die Auslieferung an den Kunden, nachdem der TÜV-Stempel da ist.

### Was ein CI-Workflow mindestens tut

Ein **Workflow** ist eine automatisierte Abfolge von Schritten, die in einer YAML-Datei (einem einfachen Textformat für Konfigurationen) im Repository definiert ist. Bei GitHub liegt er im Ordner `.github/workflows`. Ein Mindest-Workflow bei jedem PR:

1. **`npm ci`** — Installiert die Abhängigkeiten exakt nach Lockfile (nicht `npm install`, das Versionen ändern könnte).
2. **Test** — Führt die automatischen Tests aus.
3. **Lint** — Prüft Code-Stil und häufige Fehler.
4. **Build** — Baut das Projekt zusammen, um sicherzustellen, dass es kompiliert.

Dazu kommen:

- **Branch Protection** auf der Default-Branch (`main`): Required Checks (Pflichtprüfungen, die bestanden sein müssen), kein direkter Push, Review-Pflicht.
- **Preview-Deploys** (Vorschau-Versionen) dürfen Secrets der *Preview*-Umgebung nutzen, nicht die der Produktionsumgebung.
- **Agent-PRs** laufen durch dieselbe Pipeline wie menschliche PRs. Kein Überspringen, nur weil es „nur Docs" ist — wenn Docs ein Skript mitausführen, ist „nur Docs" eine falsche Beruhigung.

Ohne CI ist jede lokale „es startet auf meinem Mac"-Demo Vibe Coding in Produktionsverkleidung.

## Fehlerbehandlung und Logging

### Was Logging ist

**Logging** (Protokollierung) bedeutet: Die Software schreibt auf, was passiert. Wie ein Logbuch auf einem Schiff: „14:23 Uhr: Anfrage von Nutzer 42, Bestellung #789 geladen, Dauer 120ms." Wenn etwas schiefgeht, kann man im Log nachschauen, was passiert ist — anstatt zu raten.

### Was Fehlerbehandlung ist

**Fehlerbehandlung** (Error Handling) bestimmt, was passiert, wenn etwas schiefläuft. Gibt die App eine hilfreiche Fehlermeldung? Oder stürzt sie ab? Oder — am schlimmsten — tut sie so, als wäre alles in Ordnung, und zeigt falsche Daten?

### Was bei Vibe-Projekten typisch schiefgeht

- **Fehler werden geschluckt:** `catch { return null }` — wenn ein Fehler auftritt, gibt die App einfach „nichts" zurück. Der Nutzer sieht eine leere Seite, niemand weiß warum. Kein Eintrag im Log, keine Fehlermeldung.
- **Generische 500-Fehler:** Der Nutzer sieht nur „Internal Server Error" — ohne Hinweis, was schiefgelaufen ist. Gleichzeitig werden interne technische Details (Stack Traces — die genaue Fehlerspur durch den Code) nach außen gezeigt, was Angreifern hilft.
- **Alles wird geloggt — inklusive Secrets:** Die App schreibt den gesamten HTTP-Header ins Log — inklusive Authentifizierungs-Tokens und API-Schlüssel. Wer die Logs lesen kann, hat Zugriff auf alles.
- **Nichts wird geloggt:** Gar keine Logs. Wenn Stripe meldet, dass eine Zahlung fehlgeschlagen ist, sieht man es erst, wenn der Kunde sich beschwert.

### Der Sollzustand

- **Fehlerklassen trennen:**
  - **4xx-Fehler** (z. B. 400 Bad Request, 403 Forbidden, 404 Not Found): Der Client hat etwas Falsches geschickt. Die Fehlermeldung erklärt dem Client, was falsch ist — aber verrät keine internen Details.
  - **5xx-Fehler** (z. B. 500 Internal Server Error): Der Server hat ein Problem. Nach außen: kurze Meldung. Nach innen: detaillierter Log-Eintrag.

- **Timeouts und Retries an den Rändern:** Wenn die App einen externen Dienst aufruft (Stripe für Zahlungen, einen KI-Provider für Textgenerierung), muss sie damit umgehen, dass dieser Dienst manchmal nicht antwortet. **Timeout** (Zeitlimit): Wie lange wartet die App maximal? **Retry** (Wiederholung): Wie oft versucht sie es erneut? Diese Logik gehört an die *Ränder* (dort, wo die App mit der Außenwelt kommuniziert), nicht um die Geschäftslogik herum.

- **Strukturierte Logs:** Statt wirrer Textzeilen: klare Felder. Jeder Log-Eintrag enthält:
  - **Request-ID:** Eine eindeutige Kennung für jede Anfrage, damit man zusammengehörige Einträge finden kann.
  - **User-ID** (wenn datenschutzrechtlich erlaubt): Welcher Nutzer war betroffen?
  - **Operation:** Was wurde versucht? (z. B. „Bestellung erstellen")
  - **Dauer:** Wie lange hat es gedauert?
  - **Keine Payloads mit PII:** PII (Personally Identifiable Information — personenbezogene Daten) wie Name, E-Mail, Adresse gehören standardmäßig *nicht* ins Log.

- **Alerts an den richtigen Stellen:** Nicht bei jedem 404 (Seite nicht gefunden — das ist normal). Sondern bei Fehlern an den Geld- und Auth-Pfaden: Wenn Billing oder Login bricht, muss das Team es *sofort* erfahren — bevor die Nutzer es auf Twitter/X posten.

## Agentenfähige Übergabe

Das Ziel: Der Gründer soll nach den Umbau-Wochen *ohne euch* weiterarbeiten können — inklusive seiner KI-Agenten. Dafür muss der Kontext (das Wissen über Regeln, Grenzen und Verbote) im Repository liegen, nicht in euren Köpfen oder in privaten Chat-Verläufen.

### Was ins Repository gehört

**`AGENTS.md` / Custom Instructions:** Eine Datei, die KI-Agenten lesen und befolgen. Sie enthält:
- Architekturgrenzen: „`src/domain/` nicht ohne begleitenden Test ändern."
- Verbote: „Keine Secrets committen. Keine Tests löschen. Kein `any` in Domain-Dateien" (`any` ist ein Typ in TypeScript, der jede Typsicherheit aufhebt — in der Geschäftslogik ein Risiko).
- Konventionen: „PR-Text referenziert immer das Issue."

**Rules:** Kurz und budgetbewusst. Das Context Window (der „Arbeitsspeicher" des KI-Modells) ist begrenzt — lange Regel-Dateien fressen Platz, der für den eigentlichen Code gebraucht wird.

**Skills:** Wiederverwendbare Anleitungen für häufige Aufgaben. Zum Beispiel: „Neue API-Route anlegen: Auth-Check einbauen, Test schreiben, Fehlerbehandlung nach Standard X." Statt diese Anweisungen bei jedem Chat neu zu tippen, hinterlegt man sie als Skill, den der Agent bei Bedarf lädt.

**MCP-Allowlist:** Welche Werkzeuge darf der Agent benutzen? Dateisystem nur innerhalb des Repositories, GitHub-Issues ja, Produktionsdatenbank nein.

**Human Quality Gates:** Merge und Produktions-Deployments bleiben menschlich — wie in Kapitel 6 beschrieben.

### Die Übergabe-Session

Die Übergabe ist nicht „hier ist das Repository, viel Erfolg". Es ist ein gemeinsamer Durchlauf:

1. Ein kleines Issue aus dem echten Backlog auswählen.
2. Den Agent darauf ansetzen.
3. Die CI-Pipeline laufen lassen.
4. Der Gründer reviewed den PR und merged ihn.

Wenn der Gründer das Gate nicht bedienen kann — wenn er nicht weiß, wie er einen PR reviewed oder warum ein Test rot ist — habt ihr Software übergeben, aber kein System.

## Der Abschluss-Satz

Vibe Coding bleibt erlaubt auf unkritischen Flächen — *nachdem* die tragenden Teile Grenzen, Tests und CI haben. Wer weiter nur chattet, ohne zu prüfen, erzeugt denselben Schutt wie vorher.

Das Artefakt aus dem Audit (die Checkliste, die Risikoliste) wird zur **Definition of Done** für „Dürfen wir live gehen?". Alles, was auf der Blocker-Liste noch offen ist, geht nicht live. Das ist das Gespräch, für das der Gründer euch bezahlt — nicht ein schönerer Farbverlauf auf dem Landing-Page-Button.

<Merksatz>
Production ist CI auf jedem PR, Fehler, die ihr beobachten könnt, und Regeln, die Agenten lesen. Die Übergabe ist ein System im Repo, kein ZIP und kein Chat-Export.
</Merksatz>
