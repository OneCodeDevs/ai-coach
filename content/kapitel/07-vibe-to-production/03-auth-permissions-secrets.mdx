Vibe-MVPs haben oft eine Login-Seite, ein JWT in `localStorage` und eine API, die dem Token glaubt, ohne die Ressource zu prüfen. Der Founder sieht „Auth ist drin“. Du siehst drei getrennte Fragen: Authentifizierung, Autorisierung, Geheimnisverwaltung. Angebot 2 nennt sie explizit als Audit-Säule.

## Authentifizierung

- Wer stellt die Identität aus (IdP, Magic Link, Passwort, „wir haben Clerk copy-pasted und die Keys liegen in `.env.example`“)?
- Session vs. Token: Lebensdauer, Rotation, Logout, parallele Geräte.
- Cookies: `HttpOnly`, `Secure`, `SameSite`. Token im Local Storage ist XSS-Beute. Fraunhofer listet XSS als typisches Vibe-Loch.
- Account-Recovery und Erstnutzer: der erste User im Seed ist oft Admin ohne Passwort-Reset.

## Autorisierung

„Eingeloggt“ ist nicht „darf diese Zeile in der Tabelle“. Prüfe:

- Jede mutierende Route: Ownership oder Rolle serverseitig. UI-Verstecken zählt nicht.
- IDs in der URL: sequentielle `/api/orders/14` plus fehlender Owner-Check ist IDOR, nicht ein Randfall.
- Admin-Pfade unter `/api/admin`, geschützt nur durch Obscurity.
- Webhooks: Signaturprüfung, sonst ist euer Stripe-Handler ein öffentlicher Bestellungsfälscher.
- Agent-Tools ([MCP](/kapitel/mcp)): dasselbe Modell. Ein Tool `delete_user` mit dem Service-Token des Servers ist Confused Deputy auf MVP-Niveau.

Schreib die Soll-Matrix klein: Rollen × Ressourcen × Aktionen. Wo die Matrix im Code nicht existiert, ist Permission „im Prompt des Tages“ gelebt worden.

## Secrets

- Git-History und Client-Bundle nach Keys durchsuchen. Vibe-Agents committen `.env`, legen Service Roles in `NEXT_PUBLIC_*`, hardcoden Fallback-Secrets in `config.ts`.
- Ein Secret für DB, Stripe und OpenAI. Rotation unmöglich, Leak total.
- CI: Secrets in GitHub Environments, nicht in Workflow-YAML. Agent-Runner ohne Prod-Keys ([CI/CD in Kapitel 6](/kapitel/agentic-workflows)).
- Logging: Token und Authorization-Header nicht in Request-Logs. Vibe-Apps loggen oft den ganzen `headers`-Bag.

## Der Founder-Dialog

Frage nicht „habt ihr Auth?“. Frage: „Kann User A die Rechnung von User B lesen, wenn er die ID kennt?“ Dann: „Wo liegt der Stripe-Key, und wer hat ihn in den letzten 90 Tagen rotieren können?“ Dritte Frage: „Welche Rolle hat der Agent, wenn er eure API über MCP aufruft?“ Wenn die Antwort „dieselben Admin-Keys wie die App“ ist, ist das der Deputy aus Kapitel 5, nur ohne Cheat-Sheet. Die Antworten steuern, ob Woche 2 ein Permission-Layer ist oder ein Notfall-Incident vor dem Launch.

Fix-Reihenfolge: Secrets aus Repo und Client, Session hart machen, serverseitige Checks an den Geld- und Datenrouten, erst dann Feinschliff an der Login-UX. Ein schönerer Login auf einer undichten API ist Kosmetik. Diese Reihenfolge gehört auf die Risikoliste von Freitag, nicht in einen Chat-Refactor „Auth hübscher“.

<Merksatz>
Auth ist Identität, Permissions sind die Matrix, Secrets sind Betriebsmittel. Die Login-Seite beweist keines der drei.
</Merksatz>
