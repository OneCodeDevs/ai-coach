Viele Vibe-Coding-Projekte haben eine Login-Seite. Der Gründer sieht das und denkt: „Auth ist drin." Aber eine Login-Seite ist nur die Oberfläche. Darunter gibt es drei komplett verschiedene Fragen, die oft durcheinandergeworfen werden. Diese Lektion erklärt alle drei von Grund auf.

## Die drei Säulen: Authentifizierung, Autorisierung und Secrets

### Authentifizierung: „Wer bist du?"

**Authentifizierung** (englisch: Authentication, kurz Auth oder AuthN) beantwortet die Frage: *Bist du wirklich die Person, die du behauptest zu sein?*

**Analogie:** Du kommst an den Eingang eines Bürogebäudes. Der Portier prüft deinen Ausweis. Das ist Authentifizierung — er stellt deine Identität fest.

In Software funktioniert das über verschiedene Methoden:

- **Passwort:** Der Klassiker. Du gibst Nutzername und Passwort ein, der Server prüft, ob die Kombination stimmt.
- **Magic Link:** Du gibst deine E-Mail-Adresse ein und bekommst einen einmaligen Link per E-Mail. Wer den Link anklickt, ist authentifiziert — denn nur du hast Zugriff auf dein E-Mail-Postfach (idealerweise).
- **OAuth / IdP (Identity Provider):** Du klickst „Mit Google anmelden" oder „Mit GitHub anmelden". Ein externer Dienst (der IdP — Identitätsanbieter) bestätigt deine Identität. Dienste wie **Clerk**, **Auth0** oder **Supabase Auth** bieten das als fertigen Baustein an.

Nach erfolgreicher Authentifizierung bekommt der Nutzer eine **Session** (Sitzung) oder ein **Token** (eine Art digitaler Ausweis). Damit muss er sich nicht bei jeder Aktion erneut anmelden.

**Was im Vibe-MVP oft schiefgeht:**

- **JWT im localStorage:** Ein JWT (JSON Web Token — eine kompakte, signierte Datei, die Identitätsinformationen enthält) wird im localStorage des Browsers gespeichert. Das Problem: localStorage ist für JavaScript-Code auf der Seite zugänglich. Wenn die Seite eine XSS-Schwachstelle hat (ein Angriff, bei dem fremder Code auf der Seite ausgeführt wird), kann der Angreifer den Token stehlen. Sicherer: Cookies mit den Flags `HttpOnly` (nicht per JavaScript lesbar), `Secure` (nur über verschlüsselte Verbindungen) und `SameSite` (nur an dieselbe Website gesendet).
- **Keine Session-Verwaltung:** Wie lange bleibt ein Login gültig? Kann man sich abmelden? Was passiert bei mehreren Geräten gleichzeitig? Oft nicht durchdacht.
- **Der erste Nutzer im Seed** (Testdaten zum Start) ist Admin ohne Passwort-Reset-Möglichkeit.
- **API-Schlüssel in `.env.example`** — eine Beispiel-Konfigurationsdatei, die oft versehentlich echte Schlüssel enthält und öffentlich im Repository liegt.

### Autorisierung: „Was darfst du?"

**Autorisierung** (englisch: Authorization, kurz AuthZ) beantwortet die Frage: *Du bist zwar identifiziert — aber darfst du das, was du gerade tun willst?*

**Analogie:** Du bist im Bürogebäude drin (authentifiziert). Aber das heißt nicht, dass du in jeden Raum darfst. Die Buchhaltung ist für Buchhaltungsmitarbeiter, der Serverraum nur für IT.

In Software heißt das:

- **Eingeloggt sein reicht nicht.** „Eingeloggt" bedeutet nur: Die Identität ist bestätigt. Ob der eingeloggte Nutzer *diese spezifische* Bestellung sehen, *diesen spezifischen* Datensatz löschen oder *diese spezifische* Einstellung ändern darf, ist eine separate Prüfung.
- **UI-Verstecken ist keine Autorisierung.** Wenn ein Button für Nicht-Admins ausgeblendet wird, aber die zugehörige API-Route (der Server-Endpunkt, der die Aktion tatsächlich ausführt) keine Berechtigungsprüfung hat, kann jeder die Aktion auslösen — er muss nur die URL kennen.

**Was im Vibe-MVP oft schiefgeht:**

- **IDOR (Insecure Direct Object Reference):** Die URL sieht so aus: `/api/orders/14`. Ein Nutzer ändert die 14 zu einer 15 — und sieht die Bestellung eines anderen Nutzers. Das passiert, wenn die API nicht prüft, ob der anfragende Nutzer der Besitzer der Bestellung ist. Sequentielle IDs (1, 2, 3, …) machen das Erraten einfach.
- **Admin-Pfade nur durch Unbekanntheit geschützt:** `/api/admin/users` existiert und funktioniert — ist aber nicht abgesichert, sondern nur „versteckt". Wer die URL kennt, hat Admin-Zugang.
- **Webhooks ohne Signaturprüfung:** Wenn Stripe (ein Zahlungsdienst) eurer App mitteilt „Zahlung erfolgreich", muss die App prüfen, ob die Nachricht wirklich von Stripe kommt. Ohne diese Prüfung kann jemand gefälschte Zahlungsbestätigungen schicken.
- **Agent-Tools ohne Berechtigungsgrenzen:** Wenn ein KI-Agent ein Tool wie `delete_user` hat, das mit dem vollen Service-Token (also den höchsten Zugangsdaten) des Servers läuft, kann der Agent alles löschen — unabhängig davon, welcher Nutzer die Anfrage gestellt hat. Das nennt man **Confused Deputy** — der Agent handelt mit Rechten, die ihm nicht zustehen sollten.

**Lösung:** Eine kleine Soll-Matrix aufschreiben: Welche Rolle × welche Ressource × welche Aktion. Beispiel:

| Rolle | Bestellungen | Nutzer | Einstellungen |
|-------|-------------|--------|---------------|
| Kunde | Eigene lesen | - | Eigene ändern |
| Admin | Alle lesen | Alle verwalten | Alle ändern |
| Agent | Eigene des Auftraggebers lesen | - | - |

Wo diese Matrix im Code nicht existiert, wurden Berechtigungen „im Prompt des Tages" gelebt.

### Secrets: „Welche Schlüssel gibt es — und wer hat sie?"

**Secrets** (Geheimnisse) sind vertrauliche Zugangsdaten: API-Schlüssel, Datenbank-Passwörter, Verschlüsselungsschlüssel. Sie sind die Schlüssel zu eurem digitalen Königreich.

**Analogie:** Die Schlüssel zum Gebäude, zum Tresor, zum Serverraum. Wenn ein Schlüssel verloren geht, muss man alle Schlösser austauschen. Wenn ein Generalschlüssel verloren geht, ist alles offen.

**Was im Vibe-MVP oft schiefgeht:**

- **Secrets in der Git-History:** `.env`-Dateien (Konfigurationsdateien mit Zugangsdaten) werden versehentlich eingecheckt. Selbst wenn man sie später löscht — in der History (der vollständigen Änderungsgeschichte) bleiben sie sichtbar. Agenten committen `.env` besonders gerne.
- **Secrets im Client-Bundle:** Schlüssel in Variablen wie `NEXT_PUBLIC_*` (bei Next.js) landen im Browser des Nutzers — und sind für jeden sichtbar, der die Entwicklerkonsole öffnet.
- **Ein Secret für alles:** Ein einziger Schlüssel für Datenbank, Stripe *und* OpenAI. Wenn dieser Schlüssel geleakt wird, ist alles kompromittiert. Rotation (das regelmäßige Austauschen von Schlüsseln) ist unmöglich, weil man alles gleichzeitig ändern müsste.
- **Secrets in CI-Konfigurationsdateien:** Statt Zugangsdaten in GitHub Environments (sichere Speicher in der CI-Umgebung) zu hinterlegen, stehen sie direkt in der Workflow-YAML-Datei — lesbar für jeden, der Zugriff auf das Repository hat.
- **Token in Logs:** Vibe-Apps loggen oft den gesamten HTTP-Header-Inhalt — inklusive Authentifizierungs-Tokens. Wer die Logs lesen kann, kann sich als beliebiger Nutzer ausgeben.

## Das Gespräch mit dem Gründer

Frage nicht: „Habt ihr Auth?" Die Antwort ist immer „ja" — weil eine Login-Seite existiert.

Frage stattdessen:

1. **„Kann Nutzer A die Rechnung von Nutzer B lesen, wenn er die ID in der URL ändert?"** — Das testet Autorisierung.
2. **„Wo liegt der Stripe-Key, und wer konnte ihn in den letzten 90 Tagen austauschen?"** — Das testet Secret-Management.
3. **„Welche Rechte hat der KI-Agent, wenn er eure API über MCP aufruft?"** — Wenn die Antwort „dieselben Admin-Keys wie die App" ist, habt ihr den Confused Deputy.

## Fix-Reihenfolge

Nicht alles gleichzeitig. Die Reihenfolge nach Risiko:

1. **Secrets aus Repository und Client-Code entfernen.** Sofort.
2. **Session-Verwaltung absichern.** Lebensdauer, Rotation, sichere Cookies.
3. **Serverseitige Berechtigungsprüfungen** an den Geld- und Datenrouten. Jede Route, die Daten verändert oder sensible Daten zurückgibt, muss prüfen: Darf dieser Nutzer das?
4. **Erst dann:** Feinschliff an der Login-Oberfläche.

Ein schönerer Login auf einer undichten API ist Kosmetik. Diese Reihenfolge gehört auf die Freitags-Risikoliste aus dem Audit.

<Merksatz>
Auth ist Identität, Permissions sind die Matrix, Secrets sind Betriebsmittel. Die Login-Seite beweist keines der drei.
</Merksatz>
