## Warum dieses Kapitel existiert

Du hast jetzt verstanden, was MCP technisch ist: Rollen, Primitives, Sicherheit. Aber technisches Wissen allein verkauft kein Projekt. Dieses Kapitel zeigt dir, wie du MCP im Gespräch mit Entscheidern (Founders, CTOs, Teamleads) erklärst — ohne zu viel zu versprechen und ohne in Fachjargon abzudriften.

## Das Problem, das MCP löst — in Kundensprache

Ohne MCP passiert Folgendes: Der KI-Agent behauptet Dinge. Er „erfindet" API-Endpunkte, die nicht existieren. Er gibt dir eine GitHub-URL, die es nicht gibt. Er schreibt Code, der auf Annahmen basiert statt auf den echten Daten deines Repos.

**Mit MCP** bekommt der Agent Zugang zu den echten Werkzeugen: Er liest das echte Ticket aus dem Ticketsystem. Er sieht die echte Dateistruktur. Er fragt die echte Datenbank (lesend). Er arbeitet mit Fakten, nicht mit Fantasie.

### Der Satz, der sitzt

> „Euer Agent kann nur so gut handeln, wie die Tools, die ihr ihm gebt. MCP ist der Standard, mit dem wir dieselben Tools in Cursor, VS Code und später in CI anschließen — einmal bauen, nicht pro IDE neu kleben."

Dieser Satz funktioniert, weil er drei Dinge tut:
1. Er stellt klar, dass der Agent nicht „magisch schlau" wird, sondern gute Werkzeuge braucht
2. Er erklärt den Standardisierungsvorteil (einmal bauen, überall nutzen)
3. Er zeigt eine Zukunftsperspektive (CI = Continuous Integration, also automatisierte Abläufe)

## Die Schmerzpunkte in MCP-Sprache übersetzen

Kunden haben Probleme, die sie in ihrer Sprache beschreiben. Du übersetzt sie in MCP-Lösungen:

### „Der Agent erfindet Dinge"

**MCP-Antwort:** Resources und eng geführte Tools ersetzen den 80.000-Token-Textblock, den man bisher ins Modell kopiert hat. Statt „lies diese 50 Seiten und merk dir alles" sagt man: „Hier ist ein Tool, frag die Datenbank. Hier ist eine Resource, das ist das Schema."

Der Agent muss nichts mehr erfinden, weil er nachschlagen kann.

### „Unklar, wer was darf"

**MCP-Antwort:** Die Server-Allowlist plus Scopes (Berechtigungsbereiche) *sind* die Berechtigungsmatrix. Server X darf nur lesen. Server Y darf schreiben, aber nur nach menschlicher Bestätigung. Das ist keine abstrakte Policy — es ist die Konfiguration, die im Repo liegt.

### „Keine Validierung, keine Kontrolle"

**MCP-Antwort:** Tests und CI (automatisierte Prüfschritte) bleiben die Qualitäts-Gates. MCP liefert dem Agent den *Zugriff* auf Tools — aber nicht das Recht, ohne Prüfung in Produktion zu deployen. Der Mensch bleibt im Loop.

## Was du NICHT sagst

### Nicht: „MCP macht eure Agents autonom und sicher."

Warum nicht? Weil Autonomie aus der Schleife im Host kommt (wie oft darf der Agent allein handeln, bevor er fragt?) und Sicherheit aus Least Privilege und Reviews. MCP macht beides *anschließbar* — es liefert es nicht automatisch mit.

### Nicht: „Wir schreiben euch einen Megaprompt, dann braucht ihr keine Tools."

Das ist das Anti-Pattern aus Kapitel 1 des Kurses: Halluzination ohne Grounding. Ein Agent ohne Tools erfindet. Tools, Compiler, Ticketsystem — das sind die Wahrheitsquellen. Ein Prompt allein ist keine.

### Nicht: „Wir installieren den Marktplatz."

Das ist die Demo, nach der die Security-Abteilung den Stecker zieht. Du verkaufst nicht „20 Server aus der Community". Du verkaufst drei geprüfte Server und einen Fahrplan für den vierten (den eigenen, für die interne API).

## Demo-Skript für den Workshop

Wenn du MCP einem Team zeigst, ist dieser Ablauf überzeugend:

### Schritt 1: Agent ohne MCP

Stelle eine Frage zu einem GitHub-Issue im Repo des Kunden. Der Agent behauptet einen Endpoint, der nicht existiert. Er erfindet Ticket-Nummern. Peinlich — aber genau das passiert heute.

### Schritt 2: Derselbe Agent mit GitHub-MCP (read-only)

Dieselbe Frage. Der Agent ruft `list_issues` auf und zeigt das echte Issue mit der echten Nummer und dem echten Titel.

**Der Kontrast** — halluziniert vs. echtes Ergebnis — ist die stärkste Folie, die du haben kannst.

### Schritt 3: Filesystem-Server mit Schreibtool hinter Bestätigung

Der Agent schreibt eine Datei im Repo. Aber: Ein Bestätigungs-Dialog erscheint, der dir zeigt, *was* geschrieben wird. Ein Diff (Vergleich vorher/nachher), kein blindes Merge.

### Schritt 4: Zeigen, was NICHT angebunden ist

Genauso wichtig: Zeig, dass die Prod-Datenbank, die Secrets (Passwörter) und der Deploy-Zugang bewusst *nicht* angebunden sind. Das demonstriert Kontrolle und Least Privilege — und beruhigt die Security-Leute im Raum.

### Die Gate-Frage

Nach der Demo stellst du die Frage: „Wer darf mergen?" Die Antwort ist nie der Server. Der Mensch entscheidet, wann Code in Produktion geht.

## Einwandbehandlung

### „Ist das nicht Vendor-Lock-in?"

MCP ist das Gegenteil. Es ist ein offener Standard. Der Server, den ihr heute in Cursor nutzt, funktioniert morgen in VS Code. Lock-in entsteht, wenn ihr nur die proprietären Bordmittel einer IDE ohne Vertrag nutzt — weil euch dann niemand sonst unterstützen kann.

### „Unsere Daten dürfen nicht in die Cloud."

Perfekt — lokaler stdio-Server. Die Daten verlassen den Rechner nie. Sie gehen nur an das Modell, wenn ein Tool sie explizit weitergibt. Remote-HTTP ist eine bewusste Entscheidung mit OAuth-Authentifizierung, nicht der Default.

Falls das Modell selbst in der Cloud läuft (was bei den meisten der Fall ist): Das ist eine separate Frage vom MCP-Transport. Die Daten, die der Server dem Modell gibt, gehen ans Modell — aber der Server selbst speichert nichts in einer fremden Cloud.

### „Wir haben schon Plugins."

Plugins sind Host-spezifisch: Ein VS-Code-Plugin funktioniert nicht in Cursor, ein Cursor-Plugin nicht in Claude Desktop. MCP ist die gemeinsame Steckdose. Du baust den Server einmal, und er funktioniert überall.

### „Sicherheit?"

Die Spezifikation erzwingt nichts — aber genau deshalb liefert ihr: Allowlist (nur geprüfte Server), Pinning (feste Versionen), getrennte Tokens pro Server, Human-in-the-Loop für destruktive Aktionen, Logs. Das ist Teil des Lieferumfangs, kein optionales Add-on.

## Brücke zum nächsten Kapitel

MCP allein ist keine Delivery. Es sagt dem Agent, *was* er tun kann. Agentic Workflows (das nächste Thema) sagen, *wann* welches Tool in welcher Schleife läuft und wo der Mensch steht.

- **Ohne MCP** redet der Agent nur (und erfindet).
- **Mit MCP** kann er im Repo handeln.
- **Mit Gates** darf er das kontrolliert in Produktion tun.

<Merksatz>
Im Kundengespräch ist MCP die standardisierte Werkzeugwand im Repository. Du verkaufst Grounding und eine Allowlist, nicht Autonomie und nicht den Marktplatz.
</Merksatz>
