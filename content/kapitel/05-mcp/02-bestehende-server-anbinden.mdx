Den ersten Server anbinden ist Konfiguration, nicht Engineering. Der Fehler im Kundengespräch ist, das mit „MCP eingeführt“ zu verwechseln. Eingeführt ist MCP, wenn der Host eine kurze, geprüfte Liste von Servern hat, jeder mit klarer Aufgabe und engen Rechten.

## Wo die Config lebt

Der Host startet einen lokalen Server als Kindprozess: `command` plus `args`. Dieselbe Launch-Zeile, andere Datei.

- **Cursor:** `.cursor/mcp.json` mit Schlüssel `mcpServers`
- **VS Code:** `.vscode/mcp.json` mit Schlüssel `servers` und `type: stdio`
- **Claude Code / Claude Desktop:** analog, oft über CLI (`claude mcp add`) oder die Desktop-Config

Remote-Server nutzen Streamable HTTP plus Auth (Bearer, API-Key, OAuth). Die spezifizierte Empfehlung für Remote ist OAuth, nicht ein ewig gültiges PAT in der JSON-Datei.

Nach dem Eintrag kommt ein Trust-Prompt. Der Host zeigt, *welcher* Befehl startet. Den Dialog nicht wegklicken. Die genaue Command-Line ist die Angriffsfläche: `npx irgendwas@latest` ist ein anderes Risiko als eine gepinnte Version mit Checksumme.

## Was du zuerst anbindest

Im Repo eines Kunden zählt Grounding, nicht der Marktplatz.

1. **GitHub / Issues / PRs**, wenn der Agent Tickets lesen und kommentieren soll, ohne die REST-API zu halluzinieren.
2. **Filesystem mit Root-Begrenzung** auf das Arbeitsverzeichnis, nie `$HOME`.
3. **Datenbank read-only**, Schema als Resource, Queries als Tool mit Timeout und Row-Limit.
4. **Observability** (Sentry, Logs) als Resource-lastiger Server, nicht als Schreibzugriff auf Prod.

Offizielle und vendor-betriebene Server schlagen unbekannte npm-Pakete. Microsofts MCP-for-Beginners-Kurs ist der deutschsprachige Einstieg, den du einem Team geben kannst, das die Config selbst pflegen soll.

## Die Checkliste vor dem Merge der Config

- **Allowlist.** Jeder Server hat einen Owner im Team und einen Satz erlaubter Tools. Kein „wir haben mal 15 ausprobiert und die JSON liegt noch da“.
- **`tools/list` lesen.** Namen, Descriptions, Parameter. Ein Tool `run_command` ohne Allowlist ist eine Remote-Shell.
- **Secrets.** Tokens in OS-Keychain oder Host-Secret-Store, nicht in der committed `mcp.json`. Pro Server eigene Credentials, niemals ein Shared-PAT für GitHub *und* die Datenbank.
- **Transport.** Lokal stdio. Remote nur TLS. Loopback binden (`127.0.0.1`), nicht `0.0.0.0`.
- **Context-Budget.** Jeder Server wirft Tool-Schemas in das Fenster. Zehn Server mit je zwanzig Tools kosten Token, bevor der Nutzer eine Zeile getippt hat.

## Was du einem CTO sagst

„Wir binden drei Server an, die euer Repo und eure Tickets wahrheitsfähig machen. Alles andere kommt später, mit Owner und Scope.“ Wenn jemand eine interne API hat, die kein Server abdeckt, ist das der Moment für Kapitel 3, nicht für noch ein `npx`.

<Merksatz>
Anbinden heißt Allowlist, gepinnte Version, geprüfte Tool-Liste und eigene Credentials. Ein Host mit einem Dutzend ungeprüfter Server ist keine Plattform, sondern eine offene Werkzeugwand.
</Merksatz>
