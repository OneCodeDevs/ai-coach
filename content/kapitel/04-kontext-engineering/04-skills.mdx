Bisher hast du gelernt, wie du einem KI-Agenten **Fakten** über dein Projekt mitgibst: AGENTS.md, CLAUDE.md, Cursor-Rules, Copilot-Instructions. Alle diese Dateien beantworten die Frage: *Wie ist dieses Projekt aufgebaut?*

Aber es gibt eine zweite Frage, die genauso wichtig ist: *Wie führen wir bestimmte Aufgaben durch?* Zum Beispiel: Wie machen wir ein Release? Wie legen wir eine Datenbank-Migration an? Wie schneiden wir ein neues Feature?

Solche Verfahren (Abläufe mit mehreren Schritten, Checklisten, Prüfpunkten) gehören **nicht** in AGENTS.md oder CLAUDE.md. Warum? Weil sie dort bei **jedem** Gespräch mitgeladen würden — auch wenn du nur einen kleinen Tippfehler beheben willst. Das kostet Token und verwirrt den Agenten.

Die Lösung heißt: **Skills**.

## Was ist ein Skill?

Ein **Skill** ist eine Anleitung für den KI-Agenten, die nur dann geladen wird, wenn sie gebraucht wird. Stell dir einen Werkzeugkasten vor: AGENTS.md ist das Schild an der Werkstatt-Tür („wir arbeiten hier mit Holz, diese Säge nicht anfassen"). Ein Skill ist die detaillierte Bauanleitung für einen bestimmten Schrank — du holst sie nur heraus, wenn du tatsächlich diesen Schrank baust.

### Technisch gesehen

Ein Skill besteht aus einem **Ordner** mit einer Datei namens `SKILL.md`. Diese Datei hat:

1. **Frontmatter** (der Kopfbereich mit Metadaten zwischen `---`-Markierungen): Mindestens ein **Name** und eine **Description** (Beschreibung).
2. **Body** (der Hauptteil): Markdown-Text mit Schritten, Prüfungen, Verboten — alles, was der Agent für diese spezifische Aufgabe braucht.
3. **Optional**: Weitere Dateien im selben Ordner — Referenzen, Skripte, Templates.

Ein Beispiel für die Ordnerstruktur:

```
.claude/skills/
  billing-release/
    SKILL.md           # Die Anleitung
    references/
      checklist.md     # Zusätzliche Referenz
```

### Wie der Agent den Skill findet

Hier kommt die **Description** ins Spiel — und sie ist entscheidend. Beim Start einer Sitzung sieht der Agent **nur den Namen und die Description** aller verfügbaren Skills. Das ist billig: nur wenige Token pro Skill. Der Agent liest die Descriptions wie ein Inhaltsverzeichnis.

Erst **wenn** ein Skill zur aktuellen Aufgabe passt, lädt der Agent den vollen Body. Und weitere Dateien (aus `references/` etc.) erst, wenn der Body sie anfordert.

Dieses Prinzip heißt **Progressive Disclosure** (schrittweise Enthüllung): Der Agent bekommt Information in Häppchen, nicht als Ganzes. Das spart Token und hält den Fokus.

### Skill vs. CLAUDE.md: Die Schnitt-Regel

| Inhalt | Gehört in … | Warum? |
| --- | --- | --- |
| „Tests laufen mit `pnpm test`" | AGENTS.md / CLAUDE.md | Kurzer Fakt, immer relevant |
| „So schneiden wir ein Billing-Release (20 Schritte, Checkliste, Rollback)" | Skill `billing-release` | Langes Verfahren, nur bei Releases relevant |
| „React Hooks gehören nach `src/components`" | Cursor-Rule mit Glob oder `.claude/rules` | Fakt, nur bei React-Dateien relevant |

Wenn du das Release-Verfahren in CLAUDE.md klebst, bezahlst du 20 Schritte Context bei **jedem** kleinen Bugfix. Wenn du es gar nicht dokumentierst, erfindet der Agent eigene Git-Tags und Abläufe — Halluzination aus fehlendem Kontext.

## Wo liegen Skills?

### In Claude Code

- **Projekt-Skills**: `.claude/skills/billing-release/SKILL.md` — gehören zum Projekt, liegen in Git, werden mit dem Team geteilt
- **Persönliche Skills**: `~/.claude/skills/` (im Home-Verzeichnis) — nur für dich, z. B. dein persönlicher Code-Review-Workflow

Du rufst einen Skill auf per **Slash-Command** (z. B. `/billing-release`) oder **automatisch**, wenn die Description zum aktuellen Request passt. Das automatische Erkennen funktioniert wie eine Suchmaschine: Die Description enthält Schlüsselwörter, die der Agent mit deiner Anfrage abgleicht.

### In Cursor

Cursor hat ein analoges Konzept: wiederkehrende Workflows, die nicht permanent im Fenster liegen. Die Mechanik ist ähnlich — der Agent entscheidet anhand der Beschreibung, ob er den Skill lädt.

### Das offene Format: Agent Skills

Skills folgen einem **offenen Standard** namens „Agent Skills" — ähnlich wie AGENTS.md tool-übergreifend ist. Das bedeutet: Ein Skill, den du für Claude Code schreibst, könnte theoretisch auch von anderen Tools gelesen werden.

## Eine gute Description schreiben

Die Description ist der **Router** deines Skills — sie entscheidet, ob der Skill gefunden und geladen wird. Schreib sie so, wie ein Mensch die Aufgabe formulieren würde:

**Gut:** „When the user asks to cut a billing release, roll back a failed release, or asks about the release checklist."

**Schlecht:** „Billing stuff." (Zu vage — der Skill feuert nie, weil der Agent den Bezug nicht erkennt.)

**Auch schlecht:** „For any billing-related question." (Zu breit — der Skill wird bei jedem Gespräch geladen, das „billing" erwähnt, auch wenn es nur um eine Rechnung im Frontend geht. Dann verlierst du den Vorteil des Lazy-Load.)

Denk an Trigger-Wörter: „when adding a Prisma migration", „when deploying to staging", „when the user asks to cut a release". Je konkreter, desto besser.

## Skills sind Code

Ein wichtiger Punkt: Skills sind keine Notizen in einem Wiki. Sie liegen **im Repository**, gehen durch **Pull Requests**, haben einen **Owner** (Verantwortlichen). Genau wie Code.

Ein guter Skill endet mit einem **Prüfschritt** — einem Befehl, der fehlschlagen kann. Zum Beispiel: „Führe `pnpm test --filter billing` aus. Bei Rot: nicht fortfahren." Ein Skill ohne Prüfschritt ist ein Blogpost, kein Verfahren.

### Was nicht in einen Skill gehört

- **Geheimnisse** (API-Keys, Passwörter) — die gehören in Umgebungsvariablen
- **Kundenspezifische URLs** — die gehören in lokale, ignorierte Dateien
- **Einmalige Tickets** — die gehören in den Chat-Prompt

## Das Gesamtbild: Fakten vs. Verfahren

Hier ist die Zusammenfassung, die alles aus den letzten Lektionen verbindet:

- **Fakten** (kurz, immer relevant): AGENTS.md, CLAUDE.md, Cursor-Rules mit Always-Apply
- **Fakten** (nur bei bestimmten Dateien relevant): Cursor-Rules mit Globs, `.claude/rules/`, pfadspezifische Copilot-Instructions
- **Verfahren** (lang, nur bei bestimmten Aufgaben relevant): **Skills**
- **Zwang** (technisch erzwungen, nicht nur beschrieben): Hooks, CI-Gates
- **Externe Werkzeuge** (APIs, Datenbanken, Services): MCP-Server

Oder in einem Satz: **Fakten immer-an, Verfahren on-demand, Zwang per Hook, Tools per MCP.**

<Merksatz>
Skills sind versionierte Runbooks mit Lazy-Load. Rules sind Fakten. Wer Verfahren in die immer-an-Datei schreibt, kauft Context ohne Lieferqualität.
</Merksatz>
