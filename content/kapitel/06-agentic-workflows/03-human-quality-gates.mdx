Wenn ein KI-Agent autonom (also selbstständig) arbeitet, stellt sich sofort eine Frage: Wo darf er allein weitermachen — und wo muss ein Mensch draufschauen? Die Antwort darauf sind **Human Quality Gates** (menschliche Qualitäts-Kontrollpunkte).

## Was ein Gate ist — und was nicht

Ein **Gate** ist eine Stelle im Ablauf, an der das System *ohne explizite menschliche Entscheidung nicht weiter darf*. Der Agent liefert sein Ergebnis ab, und dann wartet er. Ein Mensch schaut drauf, sagt „ja" oder „nein", und erst dann geht es weiter.

**Automatische Checks** dagegen sind Maschinenurteile: Laufen die Tests? Findet der Linter (ein Werkzeug, das Code auf Stilfehler und häufige Bugs prüft) Probleme? Enthält der Code versehentlich eingebaute Passwörter? Diese Checks dürfen automatisch laufen und automatisch blockieren. Sie ersetzen aber *nicht* die menschliche Verantwortung für Fragen wie: „Passt diese Lösung überhaupt zu unserem Produkt?" oder „Ist das die richtige Architektur?"

**Der Unterschied ist entscheidend:** Wenn du beides vermischst, passiert eines von zwei Dingen:
- Ein Mensch sitzt in jeder Kleinigkeit und wird zum Flaschenhals (alles dauert ewig).
- Niemand schaut an den wirklich teuren Stellen hin (und es passieren teure Fehler).

## Wo ein Gate hingehört

Die Faustregel: **Platziere Menschen dort, wo eine Rücknahme teuer oder unmöglich ist.**

### 1. Vor dem Merge nach `main`

Kurze Erklärung für Nicht-Entwickler: In der Software-Entwicklung gibt es eine zentrale Version des Codes, die `main` heißt (manchmal auch `master`). Das ist die „offizielle" Version. Wenn ein Agent Änderungen macht, arbeitet er auf einer Kopie — einem sogenannten **Branch** (Zweig). Erst wenn jemand diese Änderungen in `main` übernimmt (das nennt man **Merge**, also Zusammenführen), werden sie offiziell.

Der Agent darf einen PR (Pull Request — eine Anfrage, die Änderungen zu übernehmen) öffnen. Aber er darf *nicht selbst mergen*, auch nicht mit einem Admin-Zugang. Das stellt man technisch über **Branch Protection** sicher — Regeln, die GitHub (oder ein anderes System) erzwingt: „Mindestens ein Mensch muss den Code geprüft haben", „Alle automatischen Tests müssen grün sein".

Ein KI-Reviewer (zum Beispiel Copilot Code Review) darf zusätzlich prüfen. Aber er zählt als Bonus-Signal, nicht als Ersatz für den menschlichen Reviewer — wenn eure Regel „vier Augen" heißt, müssen zwei menschliche Augen dabei sein.

### 2. Vor der Produktion

**Produktion** (oder kurz „Prod") bedeutet: das echte System, das echte Nutzer verwenden. Alles, was dort ankommt, hat Konsequenzen. Deshalb:

- Deployments (das Ausrollen neuer Software-Versionen) gehen aus `main`, nicht aus Agent-Branches.
- Änderungen an besonders sensiblen Bereichen — Authentifizierung (Login), Zahlungen, Datenlöschung, öffentliche API — brauchen ein zusätzliches Gate oder eine explizite Freigabe durch den Verantwortlichen.

### 3. Vor destruktiven Werkzeug-Aufrufen

Manche Aktionen kann man nicht rückgängig machen: eine Datenbank löschen, eine Massenmail versenden, ein Secret (Zugangsdaten) rotieren (also die alten ungültig machen und neue erstellen). Solche Aktionen brauchen eine Bestätigungsoberfläche, die dem Menschen die vollständigen Parameter zeigt — und die das KI-Modell *nicht selbst erzeugen oder umgehen kann*.

### 4. Bei Scope-Änderungen

**Scope** (Umfang) ist das, was der Auftrag umfasst. Wenn das Ticket sagt „Ändere die Buttonfarbe", aber der Agent plötzlich auch die Zahlungslogik anfasst — dann hat er den Scope eigenmächtig erweitert. Das darf nicht automatisch passieren. Ein Mensch muss den Auftrag erweitern, nicht der Agent.

Nicht jedes Issue braucht alle vier Gates. Ein Tippfehler in der README braucht nur ein lockeres Review — aber trotzdem darf der Agent nicht direkt auf `main` pushen.

## Wo ein Gate *nicht* hingehört

- **Nicht nach jedem einzelnen Schritt** in einer 40-Schritte-Sitzung. Dann kaufst du dir keine Qualität, sondern eine Warteschlange. Der Agent soll arbeiten können.
- **Nicht vor dem ersten Compile** (Übersetzen des Codes in eine lauffähige Form). Der Agent soll in seiner geschützten Umgebung (Sandbox) scheitern und es erneut versuchen dürfen — das ist der Lernprozess.
- **Nicht „irgendwann im Chat"**, ohne ein konkretes Ergebnis. Ein Gate ohne einen Diff (die sichtbaren Änderungen), ohne eine Checkliste und ohne einen Verantwortlichen ist nur ein Kopfnicken — es bringt keine Qualität.

Gute Gates sind **asynchron und ergebnisgebunden**: Der Agent erzeugt ein Artefakt (einen PR, ein Preview-Deployment, eine ausgefüllte Checkliste). Der Mensch kommt, wenn die Maschine fertig ist — nicht während sie tippt. Genau das ist der Vorteil von Cloud-Agenten gegenüber Paar-Programmierung in der IDE: Die Arbeit liegt auf einem Branch, nachvollziehbar und reviewbar.

## Gates in der Praxis verankern

Es reicht nicht, Gates mündlich zu vereinbaren. Sie müssen an zwei Stellen stehen:

1. **In den Repository-Regeln:** `AGENTS.md` (eine Datei, die Agenten lesen und befolgen) enthält: „Keine neuen öffentlichen Endpunkte ohne Auth-Test." Branch Protection in GitHub erzwingt: „Mindestens ein Review, alle Checks grün."
2. **Im Vertrag oder der Projektvereinbarung:** „Autonom" heißt: Der Agent darf recherchieren, einen Branch erstellen und Tests in der CI anstoßen — aber am Gate wartet er. „Human Quality Gate" heißt: Eine namentlich benannte Rolle (Maintainer, Gründer, Security-Verantwortlicher) mit einem klar formulierten Kriterium.

Wenn beide Quellen — die technische Konfiguration und die menschliche Vereinbarung — dieselbe Geschichte erzählen, funktionieren Gates. Wenn sie sich widersprechen, gewinnt meistens der Pfad des geringsten Widerstands — und das ist selten der sichere.

<Merksatz>
Maschinen prüfen, was maschinell prüfbar ist. Menschen stehen vor Merge, Prod und Irreversiblem. Der Agent wartet am Artefakt, er umgeht das Gate nicht mit einem überzeugenden Absatz.
</Merksatz>
