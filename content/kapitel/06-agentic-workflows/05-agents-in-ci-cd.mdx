Bevor wir über Agenten in CI/CD sprechen, müssen wir klären, was CI/CD überhaupt ist — denn der Begriff fällt ständig, wird aber selten erklärt.

## Was CI/CD bedeutet

**CI** steht für **Continuous Integration** (kontinuierliche Integration). Die Idee: Jedes Mal, wenn jemand (oder ein Agent) Code-Änderungen vorschlägt, werden diese automatisch geprüft. Automatisch heißt: Ein Computer führt Tests aus, prüft die Code-Qualität, sucht nach Sicherheitslücken — ohne dass ein Mensch das jedes Mal anstoßen muss.

**CD** steht für **Continuous Delivery** oder **Continuous Deployment** (kontinuierliche Auslieferung). Die Idee: Wenn die automatischen Prüfungen bestanden sind und ein Mensch zugestimmt hat, wird die neue Version automatisch auf dem Server veröffentlicht — also den echten Nutzern zur Verfügung gestellt.

**Analogie:** Stell dir eine Fabrik vor. CI ist die Qualitätskontrolle am Fließband — jedes Bauteil wird automatisch geprüft, bevor es weitergeht. CD ist die Auslieferung — wenn die Kontrolle bestanden ist und der Schichtleiter nickt, wird das Produkt verpackt und verschickt.

## GitHub Actions: die Maschine dahinter

**GitHub Actions** ist der CI/CD-Dienst von GitHub — die Plattform, auf der die meisten Open-Source- und viele Firmen-Projekte ihren Code verwalten. Actions führt bei bestimmten Ereignissen automatisch Aufgaben aus.

Die wichtigsten Begriffe:

- **Workflow:** Eine automatisierte Abfolge von Schritten, definiert in einer YAML-Datei (ein einfaches Textformat für Konfigurationen). Diese Dateien liegen im Ordner `.github/workflows` im Repository.
- **Event (Ereignis):** Was den Workflow auslöst — zum Beispiel: Code wurde gepusht, ein PR wurde geöffnet, ein Issue wurde erstellt, oder eine Zeitplanung (z. B. jeden Montag um 8 Uhr).
- **Job:** Eine Gruppe von Schritten, die zusammen auf einem Runner laufen.
- **Runner:** Ein Computer (meist ein virtueller Server in der Cloud), der die Aufgaben ausführt. Wie ein Mitarbeiter, der nur diese eine Aufgabe hat.
- **Step:** Ein einzelner Schritt innerhalb eines Jobs — zum Beispiel „installiere die Abhängigkeiten" oder „führe die Tests aus".
- **Action:** Ein wiederverwendbarer Baustein, den andere Leute geschrieben haben und den du in deinen Workflow einbauen kannst — wie ein Fertigteil in einem Baukastensystem.

## Zwei Rollen, die nicht verwechselt werden dürfen

### Rolle 1: CI als automatischer Prüfer

Jeder Agent-PR löst denselben Workflow aus wie ein menschlicher PR. Es gibt keinen Sonderpfad „ist ja nur der Copilot". Der Workflow tut typischerweise:

1. **Install:** Abhängigkeiten installieren (die Pakete, die das Projekt braucht).
2. **Test:** Automatische Tests ausführen — wenn etwas kaputt ist, wird der PR rot markiert.
3. **Lint:** Code-Stilprüfung — findet Dinge wie unbenutzte Variablen oder inkonsistente Formatierung.
4. **Secret-Scan:** Suche nach versehentlich eingecheckten Passwörtern oder API-Schlüsseln.
5. **Build:** Das Projekt zusammenbauen, um sicherzustellen, dass es kompiliert (also in eine lauffähige Form übersetzt werden kann).

**Required Status Checks** in der Branch Protection sorgen dafür, dass ein PR nicht gemerged werden kann, wenn einer dieser Schritte fehlschlägt. Das gilt für *jeden* PR — egal ob von einem Menschen oder einem Agenten.

Wichtig: Wenn ein Agent einen fehlschlagenden Test „repariert", indem er den Test einfach löscht, muss das entweder im Review auffallen oder an einer automatischen Policy scheitern (zum Beispiel: „Die Test-Abdeckung darf nicht unter X Prozent fallen").

### Rolle 2: Agent als Worker in Actions

GitHub Copilot Cloud Agent läuft in einer kurzlebigen Umgebung, die GitHub Actions bereitstellt: Es checkt das Repository aus, kann dort Tests fahren und Code committen. Das ist *nicht* euer Produktions-Deployment-Workflow — es ist eine Arbeitsumgebung für den Agenten.

Grenzen:
- **59 Minuten Timeout:** Danach wird die Sitzung beendet.
- **Ein Repository, ein Branch:** Der Agent kann nicht über mehrere Repositories gleichzeitig arbeiten.
- **Kosten:** Aktions-Minuten und KI-Credits laufen auf.

Trotzdem gilt: Am Ende steht ein PR, den ein Mensch reviewed und merged. Der Agent deployt nicht.

## Review-Pflicht im Detail

Damit die Trennung zwischen Agent und Mensch technisch durchgesetzt wird:

- **`main` ist geschützt.** Kein Agent-Account steht in der Bypass-Liste (Ausnahmeliste), außer das Team hat das Risiko schriftlich akzeptiert. GitHub Regelsätze können Copilot sogar *blockieren*, wenn nur bestimmte Autoren committen dürfen.
- **Mindestens ein menschlicher Reviewer.** Copilot Code Review darf zusätzlich laufen — und kostet auf privaten Repos ebenfalls Actions-Minuten.
- **Produktions-Deployments brauchen eigene Freigabe.** In GitHub Actions kann man ein `environment: production` definieren, das „Required Reviewers" verlangt. Ein Agent-PR deployt nicht automatisch in Produktion.
- **Secrets sind eingeschränkt.** Der Agent-Runner bekommt keine Produktions-Zugangsdaten. Nur die Jobs, die Secrets tatsächlich brauchen, haben Zugriff darauf.

## Was im Repository konfiguriert wird

1. Der bestehende CI-Workflow wird so eingerichtet, dass er auch auf Agent-Branches greift (Event `pull_request`).
2. Kein direkter `push` nach `main` ohne Branch Protection.
3. Optional: Ein Label oder Assignee `copilot` als Einstiegspunkt — aber nicht als Merge-Bot (der Agent schlägt vor, der Mensch entscheidet).
4. Custom Instructions oder `AGENTS.md` mit klaren Regeln: Tests nicht löschen, keine Secrets committen, PR-Text referenziert das Issue.

Der Quickstart von GitHub (ein Demo-Workflow bei `push`) ist zum Lernen der Oberfläche gedacht, nicht zum 1:1-Kopieren ins Kundenprojekt. Sobald der erste Workflow existiert, wird er genauso versioniert und reviewed wie der restliche Code.

## „Dann ist ja alles automatisch"

Nein. Automatisch ist der *Check*. Automatisch darf der Agent einen fehlschlagenden PR reparieren, indem er echten Code ändert. Automatisch ist *nicht* die Produktentscheidung. Wer beides vermischt, hat nach drei Monaten eine Codebasis, die nur noch Agenten verstehen — und Menschen können keine sinnvollen Entscheidungen mehr treffen.

<Merksatz>
CI ist das automatische Gate auf jedem PR, egal wer ihn geschrieben hat. Der Cloud Agent ist ein Worker auf einem Branch. Review-Pflicht und Production-Environment bleiben menschlich.
</Merksatz>
